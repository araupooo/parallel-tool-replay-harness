Parallel Tool Replay Harness — Findings

Record real parallel agent tool call graphs with timing and ordering, replay them deterministically, and inject timeout, cancellation, partial-failure, and out-of-order-completion faults. Every assertion is deterministic: a virtual clock replaces wall-clock time, so a replayed trace is byte-identical to the recorded one.

Reproduce

bash scripts/run_all.sh outputs/run1
bash scripts/clean_reproduce.sh   # fresh-copy run; must match run1 byte-for-byte
bash scripts/verify_digests.sh    # verifies SHA256SUMS

Requirements: Python 3.11+ (standard library only), GNU bash 5.1+ (wait -n -p), sha256sum. No network access, no credentials.

Components validated

  1. Asyncio parallel tool dispatcher (harness/): Python asyncio dispatcher running batches of parallel tool calls on a virtual clock; semantics follow the OpenAI function-calling guide (multiple calls per turn, matched by call_id) and the Anthropic parallel-tool-use guide (one tool_result per tool_use block, matched by tool_use_id).
  2. Shell parallel runner (components/shell_runner/): the same trace schema applied to real concurrent shell processes (background jobs, wait -n completion order, exit codes, output digests).
  3. Reference implementation inspection: CorbanuTerminal's parallel tool runtime (codex-rs/core/src/tools/parallel.rs, commit 7b5b368f): parallel-execution gate, CancellationToken abort path, nested-call timing guard, 3-per-turn identical-call cap.

F-02HighCancellation that drops pending calls leaves issued calls without a resultpython3 scenarios/run_cancellation.py --out-dir outputs/run1Batch cancelled at tick 4 with two calls in flight. F-03MediumAborting the batch on the first error loses later siblings' resultspython3 scenarios/run_partial_failure.py --out-dir outputs/run1The middle call fails at tick 3 with a declared `upstream 503` error. The naive gather path (`--naive-gather`, abort-on-first-error, the `asyncio.TaskGroup` pattern: "the first time any of the tasks belonging to the group fails ... the remaining tasks in the group are cancelled") aborts the batch: status `aborted`, `batch_aborted` emitted, and only 1 of 3 results reported — the later sibling (4 ticks) never reports.Per-call error isolation: the failing call is reported with `is_error: true`, both siblings complete, batch status `partial_failure`, 3/3 results reported, batch ends at tick 4.`outputs/run1/partial-failure.log`, `outputs/run1/batch-partial.trace.jsonl`, `outputs/run1/batch-partial-naive.trace.jsonl`. F-04MediumNo per-call deadline lets a slow call hold the whole batchpython3 scenarios/run_timeout.py --out-dir outputs/run1One call has a 20-tick duration. F-05LowUnguarded nested-call timing events overlap the outer call and double-count latencypython3 scenarios/run_nested_timing.py --out-dir outputs/run1An outer call (ticks 0–6) runs a nested sub-call (ticks 2–5). Without the timing guard (`--unguarded-nested`) the nested call emits its own `call_start`/`call_end` events strictly inside the outer interval; a consumer summing per-call durations counts the nested 3 ticks twice.Nested calls are excluded from timing events (CorbanuTerminal `ToolCallTimingGuard::capture`: "Suppress nested guards so consumers do not mistake overlapping events for independent tool-call latency"; test `tool_call_timing_guard_ignores_code_mode_source`). The guarded trace contains zero events with `parent_tool_call_id` set, while the outer call still returns its own result.`outputs/run1/nested-timing.log`, `outputs/run1/batch-nested.trace.jsonl`, `outputs/run1/batch-nested-unguarded.trace.jsonl`. Replay: byte-identical (`outputs/run1/replay-batch-nested.log`, `outputs/run1/replay-nested-unguarded.log`).
F-06LowUnbounded identical-call repetition loops without a per-turn cappython3 scenarios/run_repeat_cap.py --out-dir outputs/run1Four identical calls (same tool, same arguments) are issued. The fourth is refused without running: a `call_refused` event names the cap ("identical tool call refused after 3 identical calls in one turn"), the refused call never starts, and it is still reported in the result set (4/4 reported, batch status `partial_failure`).The cap mirrors CorbanuTerminal's `MAX_IDENTICAL_TOOL_CALLS_PER_TURN: u8 = 3` (`parallel.rs` line 37): repeating an identical call cannot produce new information, so the dispatcher refuses it instead of looping.`outputs/run1/repeat-cap.log`, `outputs/run1/batch-repeat.trace.jsonl`. Replay: byte-identical (`outputs/run1/replay-batch-repeat.log`).
